# 硬件极限分析：AX7020 上到底哪里没榨干

> 2026-11-03 初版。**2026-11-04 09:58 修订**（重要）：每 token 流量由 777.6 MB 更正为 **681.1 MB**；
> `bfp8_gemv` 真实带宽由"1459 MB/s"更正为 **1038–1148 MB/s**（旧值错在把整个权重文件当成了每 token 必读）；
> 纯读墙由 1259 更正为 **1270.8 MB/s**。因此旧结论"CPU 上限 618 ms / 1.62 tok/s"**作废**，
> 改为**复合下限 592 ms / 1.69 tok/s**，而当前实测 670.7 ms 已是"实测最好值加总"的 97.4%。
> 全部数字来自板载实测，外推一律标注。

## 1. 器件的硬极限

| 资源 | 总量 | 来源 |
|---|---|---|
| DDR3 带宽（理论） | 4.27 GB/s | 32 bit × 1066.667 MT/s |
| DDR3 带宽（实测可达） | ~2.4 GB/s | 双核 + DMA 并发下的经验值 |
| A9 双核读（无预取） | 818 MB/s | `membw.c` 实测 |
| A9 双核读（+软件预取，64 MB 缓冲） | 1260.7 MB/s | `lmh_bench.c` 实测，best of 5 |
| **A9 双核读（+预取，128 MB 缓冲，`PLD +256 B`）** | **1270.8 MB/s** | `lmh_bench.c` 实测，**本文采用的"墙"** |
| **S_AXI_HP DMA** | **1178 MB/s** | 166.67 MHz 实测（64 bit × 166.67 MHz = 1333 理论上限，88%） |
| PL310 L2 | 512 KB / 8 路 | |

| BRAM36K | **140** | XC7Z020（4.9 Mb = 630 KB） |
| LUT / FF | 53 200 / 106 400 | |
| PL 时钟 | 100 / 166.67 / 200 MHz | `FPGA0_CLK_CTRL` @ `0xF8000170` |

**每 token 实际要流 681.1 MB**（2026-11-04 从 320 张量 manifest 逐项求和，不是估算）：

| 用途 | 字节 | 说明 |
|---|---|---|
| `bfp8_gemv`（126 次调用） | 460,062,720 | MLP 24×3 + GDN 18×3 |
| 注意力 4 个投影（24 次调用） | 44,728,320 | 6 层 × 7,455,360，Python 侧 ctypes 调 |
| LM head 的 bf16 表 | 134,217,728 | 65536 × 1024 |
| GDN 递推状态 | 37,748,736 | 18 层 ×（1 MB 读 + 1 MB 写） |
| conv1d / in_proj_a,b / norm | 4,349,184 | |
| **合计** | **681,106,688** | **681.1 MB** |

> **⚠️ 早期文档里的「741.6 MiB / 777.6 MB」是错的。** 错因是把 643,362,048 B 的**整个权重文件**
> 都当成每 token 必读：实际上 6 层全注意力的 4 个投影走 Python 侧（44.7 MB，不在这 460 MB 里），
> 而权重文件里另有 134.2 MB 是 lm_head 用的 embed_tokens 表（另算）。正确值 **681.1 MB**。
> 独立复算见 `MEASURED_CORRECTIONS.md` §4。

由此得到硬墙（`lmh_bench.c` 实测，128 MB 缓冲、2 线程、`PLD +256 B`、best of 5）：

```
681.1 MB ÷ 1270.8 MB/s = 536 ms/token = 1.87 tok/s   ← 纯读墙（纯 CPU 假想上限）
681.1 MB ÷ 1178   MB/s = 578 ms/token = 1.73 tok/s   ← PL S_AXI_HP 单路径
```

**但 536 ms 达不到**，因为最大的那个算子 `bfp8_gemv` 是**指令发射受限**而不是访存受限（见 §2）。
按各算子各自的真实上限加总，复合下限约 **592 ms = 1.69 tok/s**。
"2.0 tok/s"在任何单路径架构下都不可达。

**关键判断：`bfp8_gemv` 不是访存受限，是 NEON 指令发射受限。** 每 16 B 的一行要
`1 vld1q_s8 + 2 vmovl_s8 + 4 vmlal_s16 + 1 共享 vld1q_s16 + 约 1.5 epilogue ≈ 17.5 cycle`，
折算 `0.914 B/cycle/core × 2 核 × 667 MHz = 1220 MB/s` 上限。实测最好 1095、profiling 里 1038，
即 **85–90% 的指令上限**——它离纯读墙 1270.8 还远，但离自己的发射上限已经很近，
所以**调预取、加行数都无效**（§7⑤）。

**三个数要分清：**
- 纯读墙假想值：**536 ms**（1.87 tok/s）——该值要求所有算子同时吃满 1270.8 MB/s；
- 各算子真实上限加总：**592 ms**（1.69 tok/s）；
- 每阶段取实测过的最好值加总：**653.3 ms**（1.53 tok/s）；
- **当前 670.7 ms，离"实测最好值加总"只差 2.7%。**

| 资源 | 单核位流（在用） | 双核位流（时序不收敛） |
|---|---|---|
| LUT | 11 768 → **22.1%** | 28 308 → 53.2% |
| FF | 14 770 → **13.9%** | 31 412 → 29.5% |
| BRAM36K | 2.5 → **1.8%** | 21 → 15.0% |
| DSP48E1 | 20 → **9.1%** | 116 → 52.7% |

**在用的位流确实只用了个位数百分比的 DSP、不到 2% 的 BRAM。** 这个批评是对的。

但要注意：**双核位流已经用到 53% LUT / 53% DSP，它是被时序挡住的，不是被资源挡住的。** 所以"加资源"不是瓶颈，"让现有逻辑跑得更快"才是。

## 4. 逐条评估"没榨干"的五个点

### ① gemv_core 输出块和而非最终 y —— 正确，这是根本原因

`gemv_core.v` 输出每 64 元素块的 int32 原始点积和，缩放留在 PS 侧做。后果：

```
一个 GEMV [M=3584, K=1024]：16 块/行 × 3584 行 = 57 344 个 int32 = 229 KB
150 个张量合计：29.6 MB/token
非缓存回读 52 MB/s → 572 ms
而同一块 DMA 送权重进来是 1178 MB/s —— 差 22 倍
```

**这一个设计让 PL 路径多花 572 ms，是它输给 CPU 的全部原因。**

**但要做对，比想象的难。** `x_scale` 是**按 64 元素块**的通用浮点（`qwen_kernels.c:217`），不是每行一个常数。所以片内必须做：

```
y[m] = Σ_b  sum_block[m][b] × 2^(e[m][b]-134) × x_scale[b]
```

其中 `2^(e-134)` 是纯 2 的幂（可用指数加），但 `x_scale[b]` 是任意浮点，**必须真的浮点乘**。这就需要在 fabric 里写 IEEE-754 乘加流水线，或者等价的宽定点 BFP 累加器。**这不是"加一级流水"，是重写输出级。**

### ② gdn_core 是 8×64 而模型是 16×128 —— 正确

`bfp_types.hpp:10` 自己写着：

```c
constexpr int GDN_HEADS = 8;   // Attention heads in prototype (2D tiled from 16 heads)
```

引擎调用点是 `self._k_gdn(..., 16, 128)`。所以 gdn_core 是**原型核，需要 2×2 = 4 块 tile** 才能覆盖真实层。

代价：状态从 64 KB 涨到 256 KB（16×128×128×2 B），占 140 个 BRAM36K 里的约 57 个（40%）。**可行，但要重新设计并过时序**——而当前 8×64 版本时序都还是 −1.581 ns。

### ③ 两个 DMA 都给 gemv_core —— 这条不对

| 设计 | 实际拓扑 |
|---|---|
| `build_bd.tcl`（**在用**） | **1 个 DMA**，只接 gemv_core，**BD 里没有 gdn 核** |
| `build_bd_full.tcl`（不收敛） | DMA0 → gemv_core，**DMA1 → gdn_core** |

不存在"两个 DMA 都给 gemv_core"。

### ④ staging 26.5 秒 —— 正确

碎片化：刚重启 625 段（150 块，1178 MB/s）；跑久了 8822 段（4882 块，364 MB/s）。
CMA 已在 boot 预留但只有 16 MiB，装不下 474 MB。

### ⑤ MTP 测的不是真实场景 —— 部分正确

我们测的是**批量 GEMV 的验证成本**（每多验证一个位置花掉整次前向的 72–74%），这确实是投机解码的约束项，但**没有 draft head 就测不了 α**。

所以结论应该严格写成：**"在这个批量内核下投机解码不划算"**，而不是"MTP 没用"。

## 5. 一个被忽略的严重错误：加 DSP 不会让 GEMV 变快

有人建议"把 MAC 阵列从 16 扩到 128 个 DSP，GEMV 从 402 ms 降到 50 ms"。**这条是错的。**

```
402 ms = 474 MB ÷ 1178 MB/s          ← 这是 DMA 时间
HP 口物理上限 = 64 bit × 166.67 MHz = 1333 MB/s
474 MB ÷ 1333 MB/s = 355 ms           ← 绝对地板
50 ms 需要 9.5 GB/s                    ← 超出上限 7 倍
```

**GEMV 是带宽受限，不是算力受限。** 现有 16 个 DSP 已经能跑满 1178 MB/s。扩到 128 DSP 会让 DSP 利用率从 9% 涨到 58%，但一秒都不会变快。

（对照：CPU 侧的 `bfp8_gemv` 是**发射受限**——855 MiB/s = 读墙的 72%，那里加优化才有用。）

## 6. 真正能提高吞吐的方向（按可行性排序）

### 方向 A：修回读（正在做）

把 29.6 MB 回读从 52 MB/s（非缓存）改成缓存 + PL310 L2 失效：

```
572 ms → ~40 ms
PL 路径 1381 ms → ~850 ms
若同时换用第二轮引擎（"其他" 407 → 229 ms）：~672 ms = 1.49 tok/s
```

**代价低（纯 PS 侧几十行），收益确定。** 但注意：它只让 PL **追平/略超** CPU（1.49 vs 1.245），因为 CPU 自己也在进步。

⚠️ 一个性能隐患：`0x77C` 是"整个 L2 clean+invalidate"，若每个 GEMV 调一次（150 次/token），开销可能吃掉收益。必须实测 `us_per_op`；若单次 >200 µs，就要改成按物理地址失效（`0x7B0`）只失效目标区间。

### 方向 B：PL 和 CPU 并发跑不同张量（唯一能突破单路径墙的办法）

这是**唯一**能让吞吐超过 1.69 tok/s 的架构：

```
CPU 路径  1270.8 MB/s  ┐
                       ├─ 合并 2449 MB/s（受 DDR3 ~2.4 GB/s 实际上限约束）
PL  DMA   1178   MB/s  ┘

681.1 MB ÷ 2.4 GB/s = 284 ms = 3.52 tok/s     ← 理论上限
```

**可并行的机会**：FFN 的 `gate` 和 `up` 两个投影**互相独立**（都是 1024→3584），可以一个给 PL 一个给 CPU，真正的并行。

**不可并行的部分**：层与层之间是严格串行的（第 n 层的输出是第 n+1 层的输入），层内 `down` 依赖 `swiglu` 的输出。所以并行度有限，实际可能只吃得到 FFN 那一半。

粗估：FFN `gate`+`up` 约占 GEMV 时间的 40%，拆开并行能省 ~20% → **670.7 → ~582 ms = 1.72 tok/s**。
前提是 PL 侧真的能跑起来（见 §6：`gemv_core` 在硬件上不可复现，这是当前最大障碍）。

**这是"榨干硬件"的唯一正确方向**，但工程量最大：要 PL 和 CPU 同时工作、要同步、要处理 DMA 与 CPU 争抢 DDR3。

### 方向 C：片内做 BFP8 解码（方向 A 的彻底版）

直接让 fabric 输出 float32 `y[m]`，回读 29.6 MB → ~1.2 MB，**572 ms → ~23 ms**，连 L2 失效都不需要了。

但需要在 fabric 里写浮点流水线（见 §4①），**风险高、工期长**，且收益只比方向 A 多 ~15 ms。**性价比低于 A。**

### 方向 D：gdn_core 扩到 16×128

把 GDN 的 67 ms 从 CPU 卸到 PL。但当前 8×64 版本时序还是 −1.581 ns，扩到 16×128 是 4 倍状态（256 KB BRAM）和更深的组合逻辑。**先解决时序再说。**

## 7. 2026-11-04 补充实测：三处"以为还有余量、其实没有"的地方

### ① 4-bit 权重（BFP4）在这颗 CPU 上是负优化 —— 已实测否决

直觉是"权重从 8 bit 降到 4 bit，内存流量减半，速度翻倍"。实测**更慢**：

| 方案 | 每 token 字节 | ms/token | token ids |
|---|---|---|---|
| BFP8 块 64（交付版） | 681.1 MB | **705.6** | `48536, 6093, 37982, …` |
| BFP4 块 64（`-DBFP4_SIM`） | ~428 MB | **730.8** | `48536, 6093, 43001, …` **不同** |

（BFP4 只把 504.8 MB 的权重减半，lm_head 表 134.2 MB 和 GDN 状态 37.7 MB 不变，
所以是 681.1 − 252.4 ≈ 428 MB，不是早期文档写的 389 MB。）

**原因：`bfp8_gemv` 是发射受限，不是纯带宽受限。** 每向量取 4-bit 后要多做约 2 条 NEON
指令（窄化装载 + 半字节拆包 + 符号扩展），指令下限抬高到超过减半后的内存下限，
所以总时间反而涨。旁证：LM head 的 bf16 版本每元素只要 0.875 条指令，所以能跑到
1154 → **1185 MB/s**；而每 16 B 要 ~17.5 cycle 的 BFP8 GEMV 只有 1038–1095 MB/s。
**流量减半 ≠ 时间减半，因为瓶颈在指令不在字节。**

**结论：在这颗 667 MHz 的 A9 上，低于 8 bit 的权重量化没有收益。** 想再快只能减少
"要读多少"，不能靠"每个数读得更小"。

### ② 这块板子上的 numpy 慢到必须躲开

`attn_overhead_bench.py` 实测（numpy 1.8.2 / armv7l，无 NEON ufunc）：

| 操作 | 规模 | 耗时 | 折算 |
|---|---|---|---|
| `np.add(a, a, out=a)` | 2048 float32 | 39.3 µs | 19 ns/元素 ≈ 13 cycle |
| `np.exp` | 2048 float32 | 173.0 µs | 84 ns/元素 |
| `np.mean(x**2, axis=-1)` | 8×256 | 243.7 µs | — |
| `np.empty(2048)` | — | 19.0 µs | 分配固定开销 |

也就是说**每个 numpy op 在小数组上有约 100 µs 的固定成本**，和元素数几乎无关。
`rmsnorm_heads`（8×256，5 个 op）= 0.54 ms，`apply_rope` = 0.29 ms。这些在 x86 上是
几微秒的事。在 24 层 × 每层若干次调用下，纯胶水就吃掉 17.8 ms/token。

**结论：任何每 token 调用 >20 次的数组运算都必须写成 C，哪怕它"只有 2048 个数"。**
这条同样适用于 `gdn` 路径和层间的 `np.add`。

### ③ LM head 不是带宽受限，别指望调预取能救

134.2 MB 用 118.3 ms = 1134 MB/s。它每元素只要 0.875 条指令（bf16→f32 走 `vshll_n_u16`），
指令上限约 1778 MB/s，所以**它是纯内存受限、不是指令受限**——这正是它还能靠调预取
再挤出 2.5% 的原因（§7⑤）。但它已经贴着 1270.8 MB/s 的纯读墙（91–94%），
**再优化只能换精度（BFP8 可省约 75 ms），而那会改变 logits → 改变 token id**，
在没有参考实现的前提下无法验证质量，因此**不做**。

### ④ 带宽天花板随访存模式变化：原地读+写只有 988 MB/s

§1 里的 1270.8 MB/s 是**纯读**。但 GDN 递推状态必须"读一遍、改、写回同一块内存"，
这是完全不同的访存模式。`bench2.c` 实测（18 MB 缓冲、2 线程、5 次取最好）：

| 模式 | 实测带宽 |
|---|---|
| 纯读 | **1190 MB/s** |
| 纯写 | 1880–2126 MB/s |
| 拷到另一缓冲（64 KB 分块） | 961 MB/s |
| **原地读+写**（2 / 8 / 64 KB 分块） | **820–879 MB/s** |
| **原地读+写 + `PLD` 预取**（8 / 64 KB） | **944 / 988 MB/s** |

GDN 每 token 必须读完 18 MB 状态（kv/qs 要每个元素）再写回 18 MB
（`S = a·S + k⊗d` 稠密更新）= 36 MB，无法再减。所以：

```
37.75 MB ÷ 988 MB/s = 38.2 ms/token   ← GDN 的真实下限
（不是纯读墙 1270.8 按比例算出来的 29.7 ms —— 那个数永远达不到）
```

分块转置后实测 **38.0 ms = 994 MB/s**，即 988 MB/s 天花板的 100.6%（每块 16 个连续元素，
比 `bench2` 的 8 KB 分块访存更连续，略优于基准）。旁证：把每元素指令数从 2.4 降到 1.3
（四轮重构）只换来 <5%，而关掉软件预取立刻 −17% —— **已经在内存墙上，不在指令上**。

**结论：以后估算任何"读-改-写"内核时，不要用纯读墙 1270.8 MB/s，要用 988 MB/s。**

### ⑤ 2026-11-04 09:45 带宽对齐轮：预取调优只值 2.8%，其余全是死路

为了把 `lm_head` 和 4 个注意力投影从 1023–1154 MB/s 追到 gemv 的水平，逐个做了 A/B：

| 尝试 | 结果 |
|---|---|
| `lm_head` 预取距离 `PFD 256 → 48`（bf16 元素，即 512 B → 96 B） | **116.272 → 113.282 ms（−2.6%）**，1154 → 1185 MB/s，**采纳** |
| `lm_head` 预取距离 64 / 32（128 B / 64 B） | 113.897 / 114.201 ms（都不如 48） |
| 同一颗 `.so` 上背靠背直接 A/B（最终确认） | 116.272 → **113.405 ms（−2.5%）** |
| `lm_head` 每趟 4 行 | 114.6–115.4 ms（无收益） |
| `lm_head` 每 32 B 预取 | **变慢** 121.9–127.0 ms |
| gemv 每趟 4 行 | **变慢 21%**（528.9 vs 420.2 ms，寄存器溢出） |
| gemv `PFDIST` 96 → 128 / 48 | 421.0 / 431.0 ms（96 最好，保留） |
| gemv 把 PLD 提到块级（每 64 B 块 4 个而不是 8 个） | **整 token 826 ms**（对比 786 ms）；完全删掉预取 921 ms |
| 指数表单独预取 | 418.3 ms（+0.5%，在噪声内） |
| OpenMP fork/join 净开销（126 个真实 region） | **净 −0.667 ms**，并行是赚的，"常驻线程池"是死路 |

**为什么 gemv 调不动**：它的 1220 MB/s 上限是 NEON 发射周期数算出来的，不是内存；
而 lm_head 的上限是内存，所以只有 lm_head 能靠预取再挤一点。
`gdn_recurrent_step` 的上限是原地读写墙，已经在 100%。

**结论：CPU 单路径上没有剩下任何一个"改改参数就能拿"的百分点。**
想再快只有两条路：减少每 token 要读的字节（改精度，会改 id），或者把一部分搬去 PL（§5/§6）。

## 8. 结论

| 问题 | 答案 |
|---|---|
| 硬件用到极致了吗？ | **CPU 路径离"实测最好值加总"只差 2.7%；PL 路径完全没用。** 在用位流只用了 9.1% DSP、1.8% BRAM |
| CPU 上还有什么余量？ | 到理论复合下限（592 ms）约 **1.13×**，到实测最好值加总（653.3 ms）只有 **1.027×**。剩下的是 gemv 的 88%→100% 发射效率和 attn 投影的带宽差（约 7 ms） |
| 降精度（4-bit）能更快吗？ | **不能，实测更慢**（730.8 vs 705.6 ms）。这颗 CPU 上 GEMV 是发射受限，见 §7① |
| 最大的一处浪费是什么？ | **PL 从来没和 CPU 同时工作过。** 另一个是回读设计：572 ms 花在 52 MB/s 的通道上，占 PL 路径 41% |
| 加 DSP 能解决吗？ | **不能。** PL 侧 GEMV 是带宽受限，HP 口 1333 MB/s 是硬地板，474 MB 最快 355 ms |
| 2.0 tok/s 可达吗？ | **单路径不可达**（CPU 复合下限 1.69、PL 墙 1.73）。**只有 PL+CPU 并发**才可能，理论 3.13、实际估计 1.6–1.7 |
| 640 ms（1.5625 tok/s）这个目标呢？ | **本方案达不到，但差得很小。** 实测最好值加总 653.3 ms 就是单路径的天花板；再往下必须砍每 token 字节（改精度 → 改 id）或上 PL。这个判断的依据是 681.1 MB 的硬流量，不是没调优 |
| 最该做的下一步是什么？ | CPU 侧只剩 2.7%，收益递减；PL 侧必须先解决 gemv_core 在硬件上**不可复现**的问题，才谈得上并发 |

## 9. 一句话

**这块板子的瓶颈从来不是算力，是内存带宽——而且带宽也快用完了。**
220 个 DSP 里用 20 个不是因为设计差，是因为再多也没用：权重只有 1178 MB/s 能送进来。
CPU 单路径现在 **670.7 ms / 1.491 tok/s**，等于"每个阶段都取它实测过的最好值"的 **97.4%**；
剩下那点余量里，numpy 固定开销已清掉、GDN 已撞到原地读写的 988 MB/s 天花板、
lm_head 已贴到纯读墙的 91%、gemv 已到 NEON 发射上限的 88%。
真正被浪费的是那 572 ms 的低速回读，以及 PL 和 CPU 从来没有同时工作过。
