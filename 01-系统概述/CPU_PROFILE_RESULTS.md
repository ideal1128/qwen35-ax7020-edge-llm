## 2. 改动明细（含失败的尝试）

### 2.1 成功的改动

**改动 A：`lm_head_argmax` 两行合并（−17.2 ms）**

原实现每行读一次 `h[i]` / `h[i+4]`（L1 命中但仍占发射槽）。改为每趟处理两行、共享 `h` 的向量装载：

- 原：每 8 个元素 8 条 NEON 指令 → 1.00 指令/元素
- 新：每 16 个元素 14 条 NEON 指令 → 0.875 指令/元素（−12.5%）

为保持 argmax 语义，行 A 先于行 B 比较（严格大于），与原升序 `t` 遍历的平局规则一致。
`lm_head` 有效带宽：999 MB/s → 1124 MB/s。

**改动 B：`bfp8_gemv` 块尾向量累加（−69.7 ms，最大单项）**

原实现每个 64 权重的块，块尾把 **8 个 int32 lane 从 NEON 拉到 ARM 核寄存器**：

```c
int32_t sa = vgetq_lane_s32(A,0) + vgetq_lane_s32(A,1)
           + vgetq_lane_s32(A,2) + vgetq_lane_s32(A,3);   // ×2 (A 和 C)
```

`vgetq_lane_s32` 在 A9 上是 NEON→核寄存器传送，约 3 周期且打断 NEON 流水线。
每 token 约 3.5M 次块迭代 × 8 = **约 2800 万次传送**。

改为在 NEON 内用 float 向量累加，整行只在最后取 1 个 lane：

```c
float32x4_t fA = vcvtq_f32_s32(vaddq_s32(a0, a1));
fs0 = vmlaq_n_f32(fs0, vmulq_n_f32(fA, EXP_SCALE[e0[b]]), g_xscale[b]);
// ... 循环结束后再 vadd_f32 / vpadd_f32 / vget_lane_f32 各一次
```

为不改变浮点结果，乘法顺序保持原样 `(dot*EXP_SCALE)*xscale`（没有合并成 `dot*(EXP_SCALE*xscale)`）。
`bfp8_gemv` 有效带宽：861 MiB/s → **984 MiB/s**（约 83% 的只读上限）。

**改动 C：`QWEN_PROFILE=1` 逐阶段计时（不省时间，是测量设施）**

在 `qwen_kernels_opt.c` 里加 `clock_gettime(CLOCK_MONOTONIC)` 计时器（15 个槽位），
导出 `qwen_prof_enable/reset/get/count/name`；引擎侧由 `QWEN_PROFILE=1` 打开，
第一个 token（warmup）丢弃，`atexit` 时打印。计时开销实测约 2 ms/次运行，可忽略。

> 编译注意：`-std=c99` 下 `struct timespec` / `CLOCK_MONOTONIC` 不可见，
> 必须在所有 `#include` 之前 `#define _POSIX_C_SOURCE 200809L`。

### 2.2 失败的尝试（都测了数字，都已回退）

**失败 1：把 gemv 预取从内层 i 循环提到块级（8 PLD/块 → 4 PLD/块）**

假设"预取指令占了 1/3 发射槽"，实测完全相反：

| PFBLK（字节） | avg | ids |
|---|---|---|
| 0（关闭预取） | 920.8 ms | `[2549, 11, 320, 278]` |
| 128 | 826.1 ms | `[2549, 11, 320, 278]` |
| 256 | 863.5 ms | `[2549, 11, 320, 278]` |
| 384 | 898.0 ms | `[2549, 11, 320, 278]` |
| 512 | 931.0 ms | `[2549, 11, 320, 278]` |
| 768 | 952.0 ms | `[2549, 11, 320, 278]` |

全部劣于基线 786.4 ms；**关闭预取最差（+134 ms）**。
结论：细粒度（每 16 字节一次）PLD 隐藏延迟的收益远大于它消耗的发射槽，原写法是对的。

**失败 2：降低寄存器压力（行 0 跑完再跑行 1，活跃 NEON 寄存器 14 → 11）**

假设"14/16 寄存器太紧导致溢出"。实测 **706.0 ms vs 697.2 ms，反而慢 9 ms**。
原因：把两条独立的依赖链串行化，损失了 ILP。已回退并保留交错写法。

**失败 3：`OMP_WAIT_POLICY=active`（自旋代替休眠）**

实测 698.6 ms vs 697.2 ms，无收益 → 272 个/ token 的 OpenMP 并行区 fork/join 开销**不是**瓶颈。
另测 `OMP_NUM_THREADS=1` = 1050.7 ms，即双线程加速比 1.51×（并行效率 75%）。

## 6. 判断：剩下的差距在哪，值不值得挖

### 6.1 先修正一下带宽模型

你给的模型是"741.6 MB / 1259 MB/s = 589 ms 下限，784 ms 里有 195 ms 非带宽开销"。

> **⚠️ 这两条都已作废（2026-11-04 更正）。** 每 token 实际流量按 320 张量 manifest 精确求和是
> **681.1 MB**（不是 741.6 / 777.6 MB），纯读墙是 **1270.8 MB/s**（1259 是单次取样，只能当"真实读数"）。
> 按这两个权威值：纯读下限 = 681.1 ÷ 1270.8 = **536 ms**；各算子按自身上限加总的复合下限是
> **592 ms = 1.69 tok/s**；"每阶段取历史最好值"的天花板是 **653.3 ms = 1.53 tok/s**。
> 见 `HARDWARE_LIMITS.md` §1/§2 与 `MEASURED_CORRECTIONS.md` §7。
> 下面各节的**相对结论**（gemv 是发射受限、int8 激活是下一步）不受影响，
> 但文中出现的 589 / 600 / 557 / 501 ms 等绝对数请按上述口径换算后再引用。

### 6.2 关键发现：gemv 是**发射受限**，不是带宽受限

这是 188 ms 里最大的可疑项，而且它不是"某个隐藏开销"，是算术本身：

一个 64 权重块 × 2 行（128 次 MAC）的指令账：

- 4 个 i 迭代 × (2 PLD + 2 `vld1q_s8` + 4 `vmovl_s8` + 2 `vld1q_s16` + 8 `vmlal_s16`) = 72
- 块尾向量累加 8
- **合计约 80 条 NEON 指令 / 128 MAC = 0.625 指令/MAC**

A9 上 128-bit NEON 指令在 64-bit 数据通路上约 2 周期，双线程再除 2：

```
452.3M MAC × 0.625 指令/MAC × 2 周期 ÷ 2 线程 ÷ 766 MHz ≈ 369 ms
```

实测 438 ms → **已达发射受限估算的 84%**。
而纯内存下限（1190 MiB/s）= 364 ms。**两个下限几乎重合（364 vs 369）**，
所以 gemv 已经没有"带宽没打满"的空间了，继续抠预取/寄存器只会像失败 1、2 那样倒退。

`vmlal_s16` 是 4 MAC/指令，这是 ARMv7 32 位累加的硬件上限，不是写法问题。

### 6.3 唯一能大幅突破的方向（需要你做决策）

把激活从 int16 降到 int8，改用 `vmull_s8` + `vpadalq_s16`（8 MAC/指令）：

- 0.625 → **0.3125 指令/MAC**，gemv 估算 438 → **约 250 ms**，整机约 **510 ms**
- 代价：M2a 已实测**相对激活漂移 1.74e-02**（ids 当时仍一致）

我**不建议**单方面上这个——它确实是精度换速度，而 1.74e-2 大于 int8 权重本身的量化误差（约 0.45%）。
要不要接受这个 trade，得你定。除它之外，靠现有 int16 算术拿不到 510 ms。

### 6.4 其余可挖项（合计约 20–30 ms，风险低）

| 项 | 现状 | 估算可省 | 说明 |
|---|---|---|---|
| `lm_head_argmax` | 119.4 ms，1072 MiB/s | ~12 ms | 已 90% 带宽，只能再压指令数（4 行合并寄存器不够，不可行） |
| `py_full_attn` 非 gemv 部分 | 约 24 ms（66.9 − 24 次 gemv 约 43） | ~10 ms | `q_and_gate[:,0,:]` 是**跨步视图**，`rmsnorm_heads`/`apply_rope` 在非连续数组上跑；改成连续缓冲 + 缓存 `.ctypes.data` 应该有收益 |
| `gdn_recurrent_step` | 52.1 ms，987 MiB/s | ~8 ms | 已高度优化（列分块、寄存器驻留），只剩带宽 |

### 6.5 600 ms 能不能到

把各阶段都压到各自的估算下限：
gemv 369 + lm_head 108 + gdn 44 + conv/gates/gated/swiglu 约 22 + py 回调非 gemv 约 14 ≈ **557 ms**。

所以：
- **600 ms 在现有 int16 算术下理论可达，但要求每个阶段都接近下限**，属于"全部都要赢"的活。
- **589 ms 这套算术的地板已作废**（正确口径：536 ms 纯读 / 592 ms 复合，见 6.1），再往下必须动 int8 激活（6.3）。
- 现实一点：把 6.4 的三项做完，**大约能到 665–675 ms**，那是我认为低风险能拿到的极限。
